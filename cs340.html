Artifact Overview

What Is This Artifact?

The CS-340 artifact is a web-based dashboard developed for the fictional nonprofit Grazioso Salvare, an international animal rescue organization that trains dogs for search-and-rescue operations. The dashboard was built using Python, the Dash framework (built on Plotly and React), and MongoDB as the backing database. Users can filter animals by rescue type — Water Rescue, Mountain & Wilderness Rescue, and Disaster & Individual Tracking — and view dynamic data tables, pie charts, and a geolocation map that updates in real time as filter criteria change.

The original implementation used basic PyMongo find() calls with dictionary-based filters. The CRUD module created a new database connection on every call, which is an anti-pattern that exhausts connection limits under load. There was no indexing strategy, no aggregation pipeline usage, no geospatial indexing, and no database-level access control — the application connected as a superuser for all operations.

This artifact was selected to demonstrate database engineering competency: not just the ability to perform CRUD operations, but the ability to design a database layer that is performant, scalable, and secure.

Enhancement Narrative

Database Design Decisions & Reflection

Justification for Inclusion

The CS-340 artifact was selected because it occupies the databases category of the ePortfolio and because the gap between the original implementation and professional database engineering practices was the largest of any artifact. The original dashboard worked for a small dataset in a development environment. It would not work correctly at scale, would not protect data appropriately, and would not take advantage of the document-oriented strengths of MongoDB. Closing that gap produced demonstrable, measurable improvements in every category that matters in production: performance, security, and maintainability.

What Was Enhanced and Why

Connection Pooling. The original AnimalShelter CRUD class instantiated a new MongoClient in its constructor, meaning every time a callback in the Dash application triggered a database read, a new TCP connection was negotiated. MongoDB defaults to a maximum of 100 connections per server. Under any realistic concurrent load, this design would exhaust the connection pool and produce ServerSelectionTimeoutError exceptions. The enhanced version implements a module-level singleton: MongoClient is instantiated once at import time, and the shared client object — which internally manages a connection pool — is passed to the CRUD class. This is the pattern recommended by the official PyMongo documentation.

Compound Indexes. Without indexes, every filter operation in the dashboard requires a full collection scan — O(n) for a collection of any size. I analyzed the dashboard's actual filter patterns and created compound indexes matching the most common query shapes: (animal_type, breed) for the type-and-breed filter, (age_upon_outcome_in_weeks) for age-range filters, and a 2dsphere index on the location GeoJSON field for geospatial queries. The ensure_index() calls are idempotent and run at startup, so they add negligible overhead and require no manual DBA intervention.

Aggregation Pipelines. The original code used find() to retrieve large result sets, then performed grouping, counting, and sorting in Python. This is inefficient: it transfers more data across the network than necessary and performs work on the application server that the database server can do more efficiently. I rewrote the analytics queries as aggregation pipelines using $match, $group, $sort, and $project stages. The pie chart data, for example, now executes a single aggregation that groups by breed and counts within the filtered set — instead of fetching all matching documents and computing the breakdown in Python.

Geospatial Queries. The original location map simply rendered latitude/longitude coordinates from the dataset without any spatial awareness. I extended the data model to store coordinates as GeoJSON Point objects and added a 2dsphere index. The dashboard now supports radius-based filtering — the user can select a rescue zone and the query uses MongoDB's $geoWithin operator to retrieve only animals within the defined operational radius.

Role-Based Database Security. The original application connected to MongoDB using a single superuser account for all operations. A read-only dashboard callback that displays data should not hold credentials capable of dropping collections or modifying indexes. I created three MongoDB database users with explicitly scoped privileges: a viewer role with find only, an editor role with find, insert, and update, and an admin role with full collection management. The application instantiates the appropriate client based on the operation being performed.

Reflection: What I Learned

This enhancement deepened my appreciation for how much work a well-designed database layer can absorb, and how much unnecessary work a poorly-designed one pushes onto the application layer. Every time I moved a computation from Python into a MongoDB aggregation stage, I gained a clearer mental model of the boundary between application logic and data logic — and how violating that boundary creates both performance problems and maintainability problems.

The geospatial indexing work was entirely new territory for me. Learning GeoJSON document structure, 2dsphere index semantics, and the $near query operator required reading through the MongoDB documentation carefully and running many test queries before the results matched my expectations. That process reinforced a professional habit I am still building: trusting the documentation over intuition when working with unfamiliar systems.

Code Sample

Aggregation Pipeline & Geospatial Query

The following Python snippet shows the refactored AnimalShelter CRUD module with the connection-pool singleton, the breed-summary aggregation pipeline used to power the pie chart, and the geospatial rescue-zone query.

# animal_shelter.py — enhanced CRUD module
from pymongo import MongoClient, GEOSPHERE, ASCENDING
from pymongo.errors import PyMongoError
import os

# --- Connection pool singleton (one client per process) ---
_client = MongoClient(
  host=os.getenv('MONGO_URI', 'mongodb://localhost:27017'),
  username=os.getenv('MONGO_USER'),
  password=os.getenv('MONGO_PASS'),
  authSource='AAC',
  maxPoolSize=50
)

class AnimalShelter:
  def __init__(self):
    self.db = _client['AAC']
    self.col = self.db['animals']
    self._ensure_indexes()

  def _ensure_indexes(self):
    # Compound index for common filter pattern
    self.col.create_index([('animal_type', ASCENDING), ('breed', ASCENDING)])
    # 2dsphere index for geospatial queries
    self.col.create_index([('location', GEOSPHERE)])

  def breed_summary(self, match_filter: dict) -> list:
    """Aggregation pipeline: count animals by breed within a filter."""
    pipeline = [
      { '$match': match_filter },
      { '$group': { '_id': '$breed', 'count': { '$sum': 1 } } },
      { '$sort': { 'count': -1 } },
      { '$project': { 'breed': '$_id', 'count': 1, '_id': 0 } }
    ]
    return list(self.col.aggregate(pipeline))

  def animals_near(self, longitude: float, latitude: float, radius_m: int) -> list:
    """Return animals within radius_m metres of a point using $geoWithin."""
    geo_filter = {
      'location': {
        '$geoWithin': {
          '$centerSphere': [[longitude, latitude], radius_m / 6378100]
        }
      }
    }
    return list(self.col.find(geo_filter, { '_id': 0 }))

  def read(self, query: dict) -> list:
    try:
      return list(self.col.find(query, { '_id': 0 }))
    except PyMongoError as e:
      print(f'Read error: {e}')
      return []

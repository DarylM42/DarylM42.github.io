Artifact Overview

What Is This Artifact?

The CS-300 artifact is a course-scheduling management program developed in C++ during the CS-300 (Data Structures and Algorithms) course. The program allows users to load course data from a CSV file, store it in a tree-based data structure, and perform searches, retrievals, and sorted listings of available courses and their prerequisites.

In its original implementation the program used a basic, unbalanced Binary Search Tree (BST). While a BST offers average-case O(log n) performance for search and insertion, it degrades to O(n) - effectively a linked list - when data is inserted in sorted or nearly-sorted order. For a course catalog that is almost always sorted alphabetically by course code, this is precisely the worst-case scenario, not a rare edge case.

This artifact was selected because the BST-to-AVL-tree upgrade is a canonical example of the kind of engineering judgment that employers value: recognizing that a correct solution is not necessarily a good solution, and knowing which data structure to reach for when performance guarantees matter.

Complexity Comparison

Operation BST (Worst) AVL
Search O(n) O(log n)

BST worst-case occurs with sorted input - the common case for alphabetically ordered course codes.

Enhancement Narrative

Design Decisions & Reflection

Justification for Inclusion

The CS-300 artifact was chosen because it directly demonstrates mastery of algorithmic complexity analysis and data structure selection - two of the most foundational skills in computer science. The original BST implementation was correct in the narrow sense of producing right answers, but it was not engineered for robustness. An employer or technical interviewer would rightly question why a developer chose an unbalanced tree for data that is almost certainly sorted. The enhancement corrects that judgment and produces a solution that is correct, efficient, and verifiably so through automated tests.

What Was Enhanced and Why

AVL Node Structure. The original BST node contained a left pointer, a right pointer, and data. I added a height field to each node. Height is recomputed after every insertion or deletion and drives the balance-factor check that determines whether rotation is necessary. The balance factor of any node must remain in the range [–1, 0, +1]; a value outside this range triggers the appropriate rotation.

Rotation Logic. I implemented all four rotation cases required for AVL rebalancing:

  • Left Rotation - applied when the right subtree is heavy.
  • Right Rotation - applied when the left subtree is heavy.
  • Left-Right Rotation - double rotation for left-heavy right subtree.
  • Right-Left Rotation - double rotation for right-heavy left subtree.

Each rotation is a pure function that takes a node pointer and returns the new subtree root, keeping the rebalancing logic completely separate from the insert/delete logic. This separation made the rotation functions independently testable.

Input Validation. The CSV parser in the original code made optimistic assumptions about data format: it would crash or produce garbage output given malformed rows, missing fields, or a file that did not exist. The enhanced version validates the file path before opening, checks each row for the minimum expected number of fields, and skips malformed rows with a descriptive console warning rather than aborting.

Unit Testing. A dedicated test file exercises the AVL tree in isolation. Tests cover: inserting already-sorted sequences (the worst case for a plain BST), verifying tree height remains logarithmic, confirming in-order traversal produces sorted output, searching for present and absent keys, and deleting leaf and internal nodes. These tests can be run with a single build target and produce pass/fail output.

Reflection: What I Learned

Implementing AVL rotations from scratch rather than using a library was a deliberately challenging choice. Working through the four rotation cases - drawing diagrams, tracing pointer assignments, and debugging balance-factor drift - gave me a far deeper understanding of tree mechanics than reading a textbook description could provide. I made mistakes: my initial right-left double rotation was updating heights in the wrong order, leading to a tree that reported itself as balanced when it was not. Catching that bug through unit tests rather than in production was a concrete demonstration of why testing matters.

I also learned to be skeptical of average-case complexity claims. The BST's O(log n) average case sounds impressive until you ask: average over what distribution? Real-world data is almost never uniformly random. Designing for the realistic worst case - sorted input for a course catalog - is what separates production-quality code from homework code.

Code Sample

AVL Insert with Rebalancing

The following C++ snippet shows the recursive insert function and the rebalancing logic that fires after each insertion to maintain the AVL height invariant. Helper functions getHeight() and getBalance() are also shown.

// avl_tree.cpp - insert with automatic rebalancing

int getHeight(Node* node) {
  return node ? node->height : 0;
}

int getBalance(Node* node) {
  return node ? getHeight(node->left) - getHeight(node->right) : 0;
}

Node* rightRotate(Node* y) {
  Node* x = y->left;
  Node* T2 = x->right;
  x->right = y; y->left = T2;
  y->height = max(getHeight(y->left), getHeight(y->right)) + 1;
  x->height = max(getHeight(x->left), getHeight(x->right)) + 1;
  return x;
}

Node* leftRotate(Node* x) {
  Node* y = x->right;
  Node* T2 = y->left;
  y->left = x; x->right = T2;
  x->height = max(getHeight(x->left), getHeight(x->right)) + 1;
  y->height = max(getHeight(y->left), getHeight(y->right)) + 1;
  return y;
}

Node* insert(Node* node, Course course) {
  // 1. Standard BST insert
  if (!node) return new Node(course);
  if (course.courseId < node->course.courseId)
    node->left = insert(node->left, course);
  else if (course.courseId > node->course.courseId)
    node->right = insert(node->right, course);
  else return node; // duplicate - ignore

  // 2. Update height of this ancestor node
  node->height = 1 + max(getHeight(node->left), getHeight(node->right));

  // 3. Check balance factor and apply rotations
  int balance = getBalance(node);

  // Left-Left case
  if (balance > 1 && course.courseId < node->left->course.courseId)
    return rightRotate(node);
  // Right-Right case
  if (balance < -1 && course.courseId > node->right->course.courseId)
    return leftRotate(node);
  // Left-Right case
  if (balance > 1 && course.courseId > node->left->course.courseId) {
    node->left = leftRotate(node->left);
    return rightRotate(node);
  }
  // Right-Left case
  if (balance < -1 && course.courseId < node->right->course.courseId) {
    node->right = rightRotate(node->right);
    return leftRotate(node);
  }

  return node; // no rebalancing needed
}
